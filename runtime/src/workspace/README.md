# Standalone workspace

The new standalone interface and SQLite application service implement the first usable slices of the [standalone workspace plan](../../../docs/superpowers/plans/2026-09-04-standalone-workspace.md). Existing runtime workspaces continue through their legacy application; no plugin or vault data is migrated automatically.

## Open the app

Latest implemented standalone interface: **28**, workspace schema: **18**. After pulling or rebuilding changes, restart the workspace launcher as well as refreshing the browser. The launcher upgrades an existing recognized workspace without automatically changing record content or approvals.

### Launch

From the repo root, after `bun install --frozen-lockfile` and `cd runtime/ui && bun install --frozen-lockfile`:

```sh
bun run workspace --demo
```

This builds and opens a **browser interface**, with synthetic advisory, investigation, and document-work examples. Keep its terminal running. Example data is saved separately in `~/.counsel/workspaces/demo/workspace.sqlite3`; your additions persist across restarts. Reopening does not duplicate the seed or reset your decisions.

For an empty personal workspace:

```sh
bun run workspace
```

Its database is `~/.counsel/workspaces/personal/workspace.sqlite3`. This remains a source-checkout app, not the final packaged installer. Use `--database /explicit/path/workspace.sqlite3`, `--port 7432`, `--no-open`, or `--skip-build` as needed; `--help` lists the options. A fresh per-process link is printed on every launch. Open that link to reconnect after restarting.

The front door is a conversation, not a choice of legal primitives. Start with a question, open a matter conversation, or attach a document. Separate chats can work simultaneously; switching chats or closing a browser tab does not stop a response while the workspace process remains open. Up to four responses run concurrently, with one active response per chat. Unsent drafts are separate and tab-local; sent messages and responses persist in SQLite.

The context panel distinguishes available documents from passages actually read, shows the matter brief and history included, and opens verified citations beside the answer. Tool activity is inspectable. Completed responses remain searchable draft history, but are not all presented as deliverables. Proposed reusable knowledge appears inline for explicit approval or rejection. Matters, knowledge, references, and search remain browsable secondary surfaces. These are real SQLite operations, not canned production responses.

### Conversations, matters, and outputs

Chats now has Active, Archived and Trash views, with rename/archive/Trash/restore actions in the history list and open conversation. Archive removes sidebar clutter but leaves scoped historical retrieval intact. Trashing a conversation suppresses its unsaved work copies from search, metadata discovery, preparation, catalog listings and direct model reads. Saved outputs/exports and decisions remain; their originating prompt is omitted from reads and search while the chat is in Trash. Applied matter updates, attached workspace files and Practice proposals/adoptions remain, with links in the action preview. Existing excerpts in other records and already-running model context cannot be retracted by this action.

Management refuses running turns and stale preview versions. Archived/trashed chats must be restored before sending. Schema 10 stores conversation, source and work lifecycle state durably, including in verified backups; schemas 5–9 remain supported for backup inspection/restore. Trash is recoverable storage, **not permanent erasure**. No existing records are automatically archived or trashed.

Documents can be explicitly added to or removed from individual matters through their reader. Adding a link grants that matter's chats access; removing one preserves the original, other links, explicitly attached chat versions and historical citations. Version-checked confirmations prevent stale changes. Documents and saved outputs have a separate **Move to Trash** preview listing retained related records. Source Trash excludes every source version from future document retrieval and inherited attachments; templates using it become unavailable. Output Trash excludes the work record from retrieval and blocks its generated Word downloads. Existing conversation messages, quoted excerpts and independent Practice records are not erased. **Trash** in the sidebar supports search and restore. Active responses using a record and stale previews block management. Permanent purge, Practice retirement and chat-driven management remain open.

Chat is where work happens. A matter brings together related conversations, documents/references, outputs/notes, decisions, and a versioned brief with open questions and next steps. Matter lists filter by scope in SQL before limiting results. The brief can be edited directly or updated through chat. It is working context, not an automatically verified status report or deadline scheduler; response context retains the version used.

When an exchange establishes useful changes, `counsel_propose_matter_brief` can prepare a full replacement for the conversation's matter. Routine summary, question and next-step updates save automatically with the successfully completed response. **Matter brief updated → See changes** shows the exact before/after; **Undo update** restores the earlier brief as a new revision, without deleting history. Undo refuses to overwrite a subsequent edit. Working notes are not a recorded human decision or a practice-standard change.

Status changes, expressly uncertain updates (`needsReview`), and updates whose starting brief changed during the response remain reviewable instead of being applied automatically. **Review matter update** shows current/proposed text; **Apply matter update** still requires the exact starting revision. A conflict preserves the answer and suggestion rather than failing the response or overwriting another chat. **Keep current brief** dismisses the suggestion. Both choices are durable and idempotent. Brief revision, receipt, completed work and evidence commit atomically. Failed/cancelled responses create neither a brief update nor an actionable suggestion. Truncated starting summaries and unchanged suggestions are refused. This does not schedule dates or automatically close matters.

“Work” is no longer primary navigation. **Saved outputs**, a secondary link beside conversations, lists substantive deliverables and existing manual notes/decisions rather than every assistant reply. The new `counsel_prepare_output` tool can name a memo, assessment, email, chronology, draft, or other substantive response; ordinary acknowledgments and discussion should not become outputs. A user can also choose **Save as output** on a completed answer. It retains that synthetic database at the printed path for inspection. The document example contains extracted text, not an uploaded DOCX; this demo does not perform legal analysis or generate documents.

## Interaction and record contract

The same conversation surface supports these starting points:

| Entry | Initial context | Durable result |
|---|---|---|
| A question | By default: this conversation's documents/work and approved practice-wide knowledge. All-matter retrieval is an explicit scope choice. | Draft work with evidence links, initially unassigned if appropriate. Assignment later preserves its ID and citations. |
| An existing matter | Its work and linked sources, plus global and matter-specific knowledge | A work record linked to that matter; prior source revisions remain inspectable. |
| A document | A source revision containing extracted text and provenance, linked to one or more matters | Work citing that exact revision, alongside the original source identity. |

Scope starts as this conversation, one matter, or all matters. It stays fixed during a response; a user may explicitly organize a previously unassigned conversation into a matter as described above. Attaching a specific saved document version explicitly permits that version, including an earlier or other-matter version. A conversation retains at most 12 attached versions. Scope is enforced in application tools and SQL before search limits; a model cannot widen it by guessing record IDs. This is a single-lawyer context boundary, not a multi-user authorization system.

Each response includes at most the latest 20 completed exchanges, bounded to 100,000 characters, plus up to 12,000 characters of matter summary. The context panel reports omitted history and the exact summary used. Attached text is fetched through tools rather than silently included in full. Reading is bounded per passage and per turn; citations require an exact quote from a range actually read in that turn.

The app instructs the model to distinguish facts, assumptions, missing evidence, prior drafts, human decisions, and approved knowledge. Those instructions still need live behavioral evaluation. Search reports extraction gaps even with zero hits. A completed response, its evidence, and pending knowledge commit atomically. Failed or stopped responses retain partial chat text but create no completed work or knowledge. Stable send IDs make retries idempotent. Stale source/knowledge reviews return conflicts instead of replacing intervening changes.

## API

```ts
import { WorkspaceStore } from './index';

const workspace = new WorkspaceStore({ databasePath: '/explicit/development/path/workspace.sqlite3' });
try {
  const matter = workspace.createMatter({ title: 'Policy advice', kind: 'advisory' });
  const source = workspace.createSource({
    kind: 'reference',
    matterIds: [matter.id],
    revision: {
      title: 'Reference note',
      body: 'Record the purpose.',
      provenance: { origin: 'user-provided reference' },
    },
  });
  workspace.recordWork({
    title: 'Initial advice', request: 'What should we document?', answer: 'Record the purpose.',
    matterId: matter.id,
    evidence: [{ target: { kind: 'source', revisionId: source.latest.id }, quote: 'Record the purpose.', start: 0 }],
  });
  const results = workspace.search({ query: 'purpose', matterId: matter.id });
} finally {
  workspace.close();
}
```

The store uses explicit database paths and UUID identities. Record operations are synchronous; binary extraction, Word generation and model runs are asynchronous and server-owned. Compound writes use immediate transactions; compound reads use a consistent snapshot. The workspace owns its application ID and schema version and refuses foreign, legacy, or newer-schema databases. Schema version 7 upgrades earlier workspace versions transactionally: v2 added conversations/settings/original registration, v3 added output metadata and matter briefs, v4 added extraction metadata, v5 added retained Word artifacts, v6 added versioned templates, and v7 adds staged imports and receipts. Existing records are preserved, not automatically classified as outputs. Storage uses Bun SQLite and FTS5; PDF intake uses the pinned `pdfjs-dist` dependency.

- **Matters:** create/get/list. `kind` is optional descriptive text, not a workflow switch. A document is not required.
- **Sources:** immutable text revisions, content hashes, provenance, and many-to-many matter links. A revision may have ready, partial, or unavailable extracted text. `reviseSource` requires the expected latest revision ID. Manually supplied original locations remain metadata and are never fetched. Explicit document uploads retain exact original bytes under `<database-path>.originals/`, with content hashes, private permissions, and registration tied to the source revision.
- **Knowledge:** immutable revisions, ownership, optional matter scope, and recorded approval metadata. New revisions default to pending. The most recent approved revision remains active while a newer revision is pending or rejected. `reviseKnowledge` also checks the expected latest revision ID.
- **Work:** immutable requests/answers with exact citations. Work defaults to a draft; a recorded human decision requires `decisionBy`. `assignWork` associates unassigned work with a matter and rejects silent reassignment. Sources need not be copied or renumbered when work is assigned.
- **Evidence:** targets an immutable source revision, knowledge revision, or prior work answer. Quotes must match at their UTF-16 offsets in the stored text. Retrieval resolves the original title, content hash, provenance where applicable, and passage. Invalid evidence rolls back the entire work record.

These are trusted application/bootstrap APIs, not model-facing tools. `approvedBy` and `decisionBy` record supplied human attribution; they do not authenticate a user. `reviewKnowledge` atomically adds an immutable approved/rejected revision and a human decision record citing the proposal (for nonempty proposal text). A stale or already reviewed proposal is refused. Earlier approved knowledge survives rejection. General proposal state, corrections, decision rationale, as-of queries, and the source → derived knowledge → advice impact graph remain unfinished. Model tools do not expose human-only review or decision attribution.

## Application boundary

`http.ts` exposes `/api/workspace` to the new interface. It uses bearer authentication with a fresh launch token, exact host/origin checks, no cookies or CORS, bounded JSON request bodies, no-store API responses, and a restrictive Content Security Policy. The server listens only on `127.0.0.1`. Public assets use the existing traversal-safe static handler; workspace records always require authentication. Browsing records makes no model calls. ## Search

Matter selection uses a shared searchable dialog in chat, assignment and import forms. Its authenticated metadata lookup searches all matter names independently of the catalog display limit, normalizes case/accents, matches every search word, and returns at most 50 results with a total count. Recent ordering uses recorded chat, work and brief activity, falling back to creation time. Full names wrap; selection never sends a message or widens an already-running chat.

The chat composer and upload panel accept dropped PDF/DOCX/TXT/Markdown files. Chat intake supports multiple files within the 12-version attachment limit, validates the selection before starting, and uploads sequentially. Successful files remain attached if a later parser fails; the remaining files are not automatically retried. Folder drops direct users to the separate reviewable importer. Uploading never calls a model. Previous user messages have a Copy prompt action preserving their exact saved text and line breaks.

`search({ query, matterId?, kinds?, includeHistory?, limit? })` searches source titles/text, knowledge titles/text, and work titles/requests/answers. Plain words are ANDed; FTS syntax is not exposed. Scope and revision filters apply before limiting results. `truncated` reports whether further matches exist.

Default results use the latest source revision and latest approved knowledge revision. `includeHistory: true` additionally includes old source revisions and pending/rejected/superseded knowledge revisions, with status and revision IDs. It is a history-inspection option, not an as-of-date query. Matter scope includes its linked sources, its work, and global or matching matter knowledge. Workspace search spans all records. Search snippets are plain text, not trusted HTML. Work hits hash the answer, not the concatenated request/search text.

`coverage.gaps` identifies partial or unavailable source text in the selected scope, regardless of query matches. `complete` means no such gaps among searched sources; it does not assert that every relevant outside source has been imported. Filtering to work or knowledge excludes source-extraction coverage. Retrieved source/knowledge details supply their category and ownership; importing an `authority` source is not a verification of its legal authority.

## Seed importer

`importSeed(unknown)` validates the `counsel-workspace-seed` format, schema version 1, dataset ID/version, records, local keys, and evidence references. Source and knowledge citations refer to the revisions imported in that dataset; a work citation may reference an earlier work record in the same dataset. The entire import and its full-text index changes commit together.

An identical retry returns the original ID map without changing user edits. Changed data or another version under the same dataset ID is refused. New dataset IDs create independent records. This is a fixture/bootstrap importer, not the future maintained-content update mechanism or legacy-workspace importer. Never use new dataset IDs as a substitute for an ownership-aware update.
