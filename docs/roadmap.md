## 1. Deadline docket — SHIPPED (v1, 2026-07-12)

**Gap:** Matter files tracked `Next Action` but nothing time-based. Legal practice runs on dates — auto-renewal windows, termination notice deadlines, sub-processor objection periods, discovery response dates. Nothing warned when a window opened or closed.

**Shipped (cou-48):** a `deadlines:` frontmatter convention on matter files (`{date, action, type, source}`), `read` proposing entries when it extracts key dates from a contract and `remember` recording them, and a read-only `/counsel-os:docket` sweep (`scripts/docket_sweep.py`) that classifies every deadline as overdue / due-soon (default 60-day window) / upcoming and surfaces malformed dates loudly. Like doctor, it changes nothing.

**How the hold was resolved:** the hold reason was task-stack *coexistence* — users already run their own task systems (Obsidian Tasks, other Claude skills), and an emit-as-Obsidian-Tasks-syntax design was parked as too unilateral. The shipped v1 coexists by *not touching* any external task system: it is a self-contained read-only sweep over the vault's own markdown, emitting into nothing. Deliberately **not** a calendar sync — a reliable local sweep beats a flaky integration. A future iteration could optionally emit into a user-chosen task system, but only opt-in.

## 2. Reference distillation

**Gap:** `remember --reference` imports third-party collections and explicitly defers "distillation as a follow-up" — but no skill implements it. Imported form books sit as a quarry; the durable payoff is mining them.

**Shape:** a skill that takes a reference collection (e.g. a 47-chapter treatise), proposes clean-room re-expressions into `practice/library/` clause variants and `practice/methods/` checklists, drops stale citations, and lets current `law/` supply the legal claims. Always user-approved; copyright note in `remember.md` already sets the re-expression constraint.

## 3. Matter status one-pager — ON HOLD (2026-06-12)

**Gap:** No single view of the practice. Stage, `updated:`, and next actions live in per-matter frontmatter; seeing the whole desk requires opening files.

**Shape:** `/counsel-os:status` — one table: open matters, stage, days since update, next action, upcoming deadlines (once #1 exists). Read-only; pairs with retro (analytics over time) the way a dashboard pairs with a report.

**Hold reason:** parked alongside #1 — same task-stack-coexistence question.

## 4. Document QA (definitions, references, party names)

**Gap:** Mechanical contract defects survive careful review because checking them by eye is tedious: defined-but-never-used terms, used-but-never-defined terms, capitalization drift ("Confidential Information" vs "confidential information"), cross-references to sections that don't exist, exhibit lists that don't match the attached exhibits, inconsistent party names. An observed audit contract used nonexistent entity names; human review caught the defects.

**Shape:** a deterministic `scripts/check_document.py` (python-docx) producing a findings list, surfaced as a `read --qa` mode and run automatically as the last step of full document review. Zero judgment risk — pure tedium automation, the highest want-it-tomorrow item on this list.

## 5. Clause-level precedent pull

**Gap:** "What have we *actually signed* for this clause?" is answerable only at deal granularity today (entity files, matter history). At drafting time a lawyer wants clause granularity: every liability cap, every confidentiality survival term, as executed, side by side with the library's proposed variants and the reference quarry.

**Shape:** `research --precedent <clause-type>` — pulls the `practice/library/` variants, the closest as-executed language (knowledge-base search over entity files and imported executed agreements), and matching reference-collection samples into one comparison. Depends on executed agreements being in the searchable vault (import_reference covers this).

## 6. Negotiation prep brief + concession ledger

**Gap:** Walking into a negotiation call requires hand-assembling counterparty history, open asks, and — critically — the running give/get balance across rounds. `diff_rounds.py` classifies what *they* did to *our* asks; nothing tracks what *we* have conceded cumulatively, which is the number a negotiator needs before agreeing to the next give. An observed negotiation-call package required this manual assembly.

**Shape:** a prep mode (research or draft) that assembles: entity history and drift patterns, current round's open items, the concession ledger (maintained per-round in the matter file by `remember`), and pre-approved fallback positions annotated from the standards bands ("if they reject 12 months, YELLOW authorizes to 24"). Output is a one-page call brief.

## 7. House-template drift

**Gap:** Counsel reviews *counterparty* paper against current standards all day, but nothing checks the user's *own templates* when standards move. When a position changes (e.g. the 2026-06-11 deletion-window decision), house forms silently keep the old language — the inverse of contract review, and a classic in-house failure mode.

**Shape:** a template registry (frontmatter-marked files or a config list pointing at the house forms) plus a drift check — doctor-style or part of `--consistency` — comparing each template's numeric/positional terms against current `practice/standards/`: "your standards changed; these templates still carry the old position."

## 8. Execution package prep

**Gap:** The path from final redline to signature is manual: produce the accept-all clean copy, add signature blocks, check the deal value against the signing-authority matrix, verify exhibit completeness, sweep effective dates. Live evidence: the Decrypt matter required a manual signing-authority check (under-$100K threshold) and caught a contracting-entity mismatch late.

**Shape:** a draft mode: from the final tracked-changes .docx, generate the execution version (docx tooling already exists), insert signature blocks per the contracting entities, flag the signer per the vault's signing-authority matrix vs. deal value, and emit an execution checklist (exhibits present, dates filled, entity names consistent — reusing #4's checker).

## 9. Standalone legal workspace — ACTIVE DIRECTION (2026-09-04)

Verification at that checkpoint: 378 backend tests, 743 UI tests, typechecks and desktop/mobile checks.

**Selected-file checkpoint (September 8, interface 22 / schema 15):** local import link analysis now resolves explicit relative Markdown/wiki references within selected roots and reports missing/ambiguous/excluded/outside targets. **Background-import checkpoint (September 8):** interface 21 / schema 15 adds durable background, content-informed import organization with reviewable matter matching, cross-batch proposed-group reuse, evidence/confidence, pause/resume and separate final import. Arbitrary supported file/folder layouts need no plugin convention. Verification: 362 workspace backend tests, 735 UI tests, both typechecks, desktop/mobile browser flows and a two-request synthetic live Codex/Sol import check pass. Earlier citation recovery, corrected model choices, retrieval, source currency, native Word, sidebar and recovery work remains implemented. The [implementation plan](superpowers/plans/2026-09-04-standalone-workspace.md) records successes and remaining gates separately. Packaging has not started.

**Outcome:** an installable, single-lawyer workspace that composes read, research, evaluate, draft, and remember around the user's intent. Matters, references, knowledge queries, documents, automatic recordkeeping, reviewed learning, and versioned content updates are core capabilities. The plugin may support a smaller feature set.

**First milestone:** substantive work grounded in sources and prior matters, followed by durable recordkeeping and later recall. Verify it across research/advice, compliance or investigation, and document work, plus a content-update scenario. See the [architecture](architecture/standalone-workspace.md) and [implementation plan](superpowers/plans/2026-09-04-standalone-workspace.md).

**Implemented:** [app-owned SQLite records and a chat-first standalone interface](../runtime/src/workspace/README.md), with independent concurrent chats, explicit context scope, real retrieval/tool activity, exact-passage readers, automatic response recording, and inline human review of proposed knowledge. Matters and libraries remain browsable. Word, PDF and UTF-8 text uploads retain original bytes. Claude Code, Codex subscription and Anthropic/OpenAI API adapters are wired but not live-qualified. Claude Code includes an explicit billing choice and a local sign-in check without model calls. `bun run workspace --demo` opens a separate synthetic workspace; `bun run workspace` opens a personal one.

**Profile added:** single-user identity and optional practice/writing preferences, saved attribution for explicit reviews and decisions, and inspectable per-response profile snapshots. Sharing can be disabled for future responses. Setup makes no model call, preserves historical names, and does not import the separate plugin profile.

**Matter and document update:** removed Work from primary navigation. Matters now collect conversations, documents, saved outputs/notes, decisions, and a versioned user-maintained brief. Ordinary replies remain searchable history; substantive named outputs retain their originating conversation and evidence. Unassigned conversations can join a matter through explicit sharing confirmation. DOCX/PDF import retains originals, extraction notes and PDF page locators; authenticated downloads verify original hashes.

**Word output added:** completed answers export directly from chat or the reader with editable structure, retained status, and a linked source appendix. Generated bytes and snapshots are stored atomically in SQLite, reusable on retry and downloadable after restart. Exported answers are discoverable as outputs without duplicating their work records. No model call or Office installation is required for export.

**Recovery and revision handling added:** Settings can download and verify a manual, unencrypted workspace backup; the development launcher restores it into a separate copy without reconnecting AI or resuming model calls. Source text/document updates retain prior originals/citations and expose version history. Earlier work is flagged when its directly cited source or approved knowledge has a newer active version. Practice-owned knowledge can be edited inline before approval or revised later; edits remain pending while the earlier approved version stays active. Maintained content cannot be directly overwritten. Broader indirect-impact analysis, scheduled/encrypted backup and in-app recovery switching remain open.

**Chat-led matter updates added:** completed responses can offer a reviewable matter-brief replacement, with current/suggested text and status. Acceptance is revision-checked against the context used by that response, preserves the answer/evidence and is idempotent; dismissal leaves the brief unchanged. Models cannot apply updates or silently close matters. A model-free provider-test runner now rehearses advisory, investigation and document work, including concurrent chats, citations and Word outputs. Live subscription checks require explicit usage consent; automated checks do not qualify reasoning quality.

**September 5 additions:** Practice/Sources naming, a sanitized Markdown reading view with exact saved-text access, and versioned practice templates with explicit sharing and pinned chat retrieval. Model selection now lives in the composer and persists per chat; catalog metadata is distinct from qualification. The Codex direct-tool configuration is fixed and three synthetic Sol workflows pass, without establishing full qualification. Folder/file staging, reviewable local naming suggestions, original retention, resumable uploads, optional reviewed profile import and atomic commit are implemented. **Remaining (current, supersedes earlier next lists):** broader document restructuring/earlier-revision handling beyond the now-qualified native Word corpus; broader context discovery and legal-source coverage/maintained currency; provider/platform and authentication-renewal qualification. The bounded import, filing, original-Word, explicit dependency and crash-recovery slices above are implemented, not still queued. OCR, automatic model routing, a comparable model scoreboard, shared workspaces and comprehensive unsupervised brief updates remain deferred. Routine single-matter notes already update automatically with inspectable receipts and undo; status changes and Practice-wide changes retain review. Broad legacy-runtime migration remains separate from explicit file/plugin imports. Packaging is held for the user's next phase.

**Provider scope:** the user explicitly wants installed Claude Code/Codex CLI use as well as APIs, with each connection requiring behavioral qualification. Claude Code remains unmodified and owns the user's authentication under [Anthropic's product integration rules](https://code.claude.com/docs/en/legal-and-compliance#can-customers-offer-claude-code-in-their-products); Counsel does not collect subscription credentials. This supersedes the earlier blanket approval gate. Plugins are unchanged. Defer Ollama, arbitrary endpoints, additional vendors, routing, and the model scoreboard. No silent subscription-to-API billing fallback; existing catalog entries do not establish support.

**General import gate:** background content-informed grouping, candidate existing-matter matching, cross-batch consistency, durable progress and focused uncertainty review are now implemented and tested on bounded synthetic corpora. Clear suggestions can be applied across pages; manual corrections and final import remain guarded. Full company/client relationships, cross-root links, complete plugin instruction migration, duplicate-versus-version migration quality and broader messy-corpus qualification remain open. Known plugin formats are optional enrichments, not a required layout. Qualify the user's two-folder migration separately before packaging; report unsupported formats and extraction gaps explicitly.

**Not prerequisites:** shared orchestration, symmetric Markdown/SQL adapters, Codex plugin packaging, or plugin feature parity. Packaging, usable onboarding, recovery, and backup/restore are part of milestone completion.

### Historical v0.15 distribution plan — superseded

The following records the earlier packaging approach. Its provider discovery, subscription-first setup, and plugin hand-off assumptions are not requirements for the current milestone. Shipped implementation details should be checked against the code.

**Gap:** the multi-model runtime and the web UI (v0.10.0) run only from a source checkout: Bun, `bun install` twice, `bun run ui:build`, `bun runtime/src/cli.ts serve --vault … --open`, plus per-provider login or `~/.counsel-os/providers.yaml` whose shape lives only in source. The plugin is one marketplace command; the runtime is a developer install. A lawyer cannot run it.

**Target:** one installer, three entry points that all reach the same thing.
- **Compiled `counsel-os` binary** (`bun build --compile`, the pattern the browse skill already uses) with the prebuilt `runtime/ui/dist` embedded, published as release assets (darwin-arm64, linux-x64) by `release-binaries.yml`.
- **Installer script** (`curl -fsSL https://eigenlegal.com/install.sh | sh` or the GitHub raw equivalent): downloads the right binary, verifies its checksum, puts it on PATH, runs `counsel-os doctor` (finds `claude` / `codex` logins, Ollama, API keys), and prints the one command to start. Homebrew tap as a follow-up.
- **Plugin hand-off**: `/counsel-os:serve` downloads the binary on first use exactly as browse does (`COUNSEL_OS_NO_DOWNLOAD=1` to disable) and opens the UI, so an existing plugin user is one slash command from the runtime.
- **First run in the UI**: with no `providers.yaml`, the picker shows what was detected and a one-click enable per provider; the Settings page already edits the registry.
- **Runtime-owned setup (stage 1 shipped, unreleased — spec `docs/superpowers/specs/2026-09-01-runtime-owned-setup-design.md`)**: the runtime carries the content, `counsel-os init` seeds a vault, and `serve` starts in setup mode with a setup API instead of exiting. Next: the first-run screen (mocks under `docs/superpowers/specs/img-standalone/`), the sample matter, content updates, doctor.
- **Docs**: a runtime page (install, serve, model setup per provider incl. the subscription logins, the token URL, `providers.yaml`), a README section, eigenlegal.com/docs.

**Not in scope:** hosted/multi-tenant, auto-update (the plugin's `/counsel-os:update` covers the plugin; the binary re-downloads on version mismatch), Windows (later; the vault path rules already reject backslashes).
