# Routing and evals, step 3 — the scoreboard

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox syntax.

**Goal:** turn the results record into a per-practice scoreboard (task × provider, three fixture sets kept apart), reachable from the API, the CLI and a "Models" group in Settings; ship the fixtures through the content source so the compiled binary can list and run them.

**Architecture:** a pure `scoreboard(results, fixtures)` over `EvalResult[]` (latest line per fixture+document per provider+model, per set), a `GET /evals/scoreboard` route plus `GET /evals/estimate` for the confirmation line, `counsel-os eval --scoreboard`; the fixture loader reads the shipped set through `ContentSource` (`evals/fixtures`, `evals/vaults` become shipped roots) and prepares a fixture vault from either a directory (practice) or the content source (shipped); a `ModelsGroup` component in Settings driven by the two routes and the existing `POST /evals/run` SSE stream.

**Tech stack:** Bun, TypeScript, zod, React 18, react-aria (none new), happy-dom tests.

**Spec:** `docs/superpowers/specs/2026-09-02-routing-and-evals-design.md` §5, §9, §10, §11 step 3, §12.

## Global constraints
- Practice, shipped and benchmark results are never averaged together; `score: null` is never averaged.
- No pills, no colour bars, set-text scores, small-caps run-ins; the rail plate untouched.
- No paid model calls in tests; the fake provider only.
- Commits carry no Co-Authored-By / Claude-Session trailers.
