### September 10: draft recovery, setup and local installation image

This checkpoint supersedes the initial shell's draft/onboarding limitations below. Interface 29 / schema 19 adds `workspace_drafts`, not a second conversation or settings store. Strict, bounded drafts contain exact chat text, retained attachment IDs, existing scope selections and non-secret model choices, or incomplete working-preference fields plus their original applied revision. They never enter retrieval, prompt context or applied preferences just by being saved. The settings save boundary remains strict even when an unfinished filename pattern is recoverable. Backup validation accepts the new table and previous schema-18 backups; restore retains drafts without activating them or reconnecting AI.

Draft writes serialize through a debounced client controller and use revision/operation IDs on the server. Same-operation retry is idempotent; conflicting windows preserve both the stored draft and still-copyable local text. Deletion leaves a revision tombstone so older tab caches cannot revive discarded drafts. A sent prompt consumes its matching draft inside the conversation transaction; late writes also check the accepted client ID. Navigation waits for draft acknowledgement and stays on the current editor on failure. Fresh windows expose recoverable entries in Chats and reopen unapplied working-preference edits in Practice. No credentials, arbitrary settings or model calls are allowed through draft endpoints.

The native shell waits for the same draft flush before confirming quit. Keep working is the safe default when saving fails; deliberate quit without the latest edits remains explicit. ### September 10: initial native macOS shell

`desktop/macos` provides a narrow Swift/AppKit/WebKit wrapper, not a second legal-work runtime. `EngineProcess` owns one exact child and receives its protocol-1 readiness message through private stdout. PID, database, embedded build ID, strict loopback origin and capability shape are checked before opening the window. The capability is not an argument, log or file. Desktop launch requires an explicit database, allows ephemeral port allocation and disables browser opening. Its handler uses the actual bound origin. The shell never scans ports, adopts another server or kills an existing process. Its open stdin pipe is a lifetime lease: EOF on quit or parent death invokes the engine’s existing bounded cleanup. Startup and shutdown have bounded fallback handling.

`WorkspaceWindow` hosts the existing UI in a nonpersistent WebKit store, pinned to its own origin. It offers native file/folder dialogs and staged native downloads, basic app/edit/navigation menus and startup/failure/quit states. External clicked HTTP(S) links go to the system browser; untrusted navigation and download redirects are refused. There is no native-message bridge or page-controlled filesystem/process API. Download destinations come from a save panel, not page-supplied paths. New downloads stage in a private sibling folder, with guarded replacement of an existing approved file; changed destinations retain the downloaded copy instead of being overwritten. Normal quit clears incomplete tracked downloads. Abrupt download interruption/recovery and full native-dialog interaction still need qualification.

The native store intentionally holds no durable browser cache. Existing unsent chat/form drafts remain browser-session-only and can be lost on quit, reload or a window crash. The shell warns before quit; durable draft recovery is the next functional gap, not a completed autosave capability. All committed records and import queues remain in the external SQLite workspace. Production entry targets the existing personal workspace; testing injected only new synthetic paths. It did not open the production entry against private data, install the app, launch live AI, change connection settings or restart the running browser workspace.

### A. Research and advice, without an uploaded agreement

Seed two prior advisory matters, an approved practice position, and an imported reference with distinguishable authority. Ask what was previously advised, then request new guidance.

The app finds the relevant prior work, distinguishes the practice position from the reference, cites the exact revisions used, and records the new work under an appropriate matter. An unrelated matter is not cited as evidence. A missing source or incomplete index is visible. A broad question can be answered before the user assigns it to a matter; assignment preserves its work and source links.

After reopening, a follow-up can recover what was advised and why without relying solely on transcript replay. A workspace-level query finds the new work and identifies whether it was a draft or a recorded decision.

### B. Compliance or investigation

Seed an open matter with evidence, unresolved questions, a confirmed deadline, and prior analysis. Ask for a status assessment and a draft internal note.

The app distinguishes evidence from inference, preserves unanswered questions, drafts the note, and records the work automatically. It does not turn its own tentative recommendation into the lawyer's decision or silently close the matter.

An approved reusable learning item becomes searchable in later work. A rejected proposal remains in history and does not become active knowledge. A correction preserves what it corrected and is reflected in subsequent answers.

### C. Document work

Import a synthetic DOCX into a matter and assess it using references and approved knowledge. Inspect findings beside their cited source passages, discuss a finding, and request a draft or redline.

Retain the original, the version assessed, the proposed changes, and the generated output with their relationships. The user can decide on changes and export the resulting artifact. A source edited after a proposal was prepared triggers a conflict or explicit rebase rather than applying stale changes silently. Reopening retains the findings, artifact, and decision history.

### D. Content update and historical recall

Deliver a test bundle containing an updated maintained source and a changed practice seed. Record the received versions. Apply maintained content according to ownership and the configured update policy; preserve user-owned knowledge.

Show a review notice for work linked to the changed source. A historical question still resolves the old citation and advice; a new question can use the new active version. An unavailable update source produces a visible stale/unavailable state, not an assertion that content is current. This tests version handling, not automated verification of real-world law.

Include these assertions:

- Retain the changed practice seed as a received upstream revision. Present its differences for review and leave the user's active knowledge unchanged until approval. Pending or rejected updates never appear as active knowledge.
- Include a dependency from a maintained source through an approved knowledge item to advice that cites only that item. A source update flags the indirectly dependent advice as well as directly cited work.
- Query as of before receipt, after receipt but before approval, and after approval. Return the knowledge active at each time. Preserve later corrections alongside the original advice, and distinguish recorded timestamps from any effective date stated by the source.

## Implementation order

### 1. Define the interaction and record contract

Sketch the entry from a question, a matter, and a document using the same workspace. Show where evidence, prior work, generated outputs, automatically recorded activity, and proposed knowledge changes appear. Include no-source, incomplete-search, failed-work, and pending-decision states.

Name the stable identities and links needed by scenarios A–D. Finalize the smallest record contract needed for those examples before building a full schema or redesigning every page. This is a bounded design pass; broader visual polishing can follow a working slice.

### 2. First coding slice: persist, search, and recall a matter's evidence

Create an app-owned workspace database and service in a separate development workspace. Start with matters, source revisions, matter/source links, knowledge revisions, work records, and evidence links. Record enough structured state to distinguish a draft answer from a user decision. Keep substantive text as text and use explicit IDs rather than paths as relationships.

Add a versioned fixture/seed importer and a scoped full-text search operation. The service must support:

- creating an advisory matter without a document;
- adding reference text or an existing document's extracted text with provenance;
- linking the same reference to several matters without losing its identity;
- recording work and the exact source/knowledge revisions used;
- retrieving within a matter or across the workspace, with inspectable source links;
- closing and reopening the database and obtaining the same records and citations.

Use one migration owner for the database. This slice does not require filesystem counterparts, a universal repository framework, embeddings, or provider calls. It should be independently testable with synthetic records. Integrating it into the application comes in the next slices; a repository test is not a completed user workflow.

### 3. Add recordkeeping, proposals, and update semantics

Add matter activities, corrections, proposals, decisions, and content-version state. Transactions cover related database changes. Use stable operation IDs so retries do not duplicate records. A proposal targets a known revision; concurrent edits produce a visible conflict.

Routine work history and generated summaries can be recorded automatically. Inferences remain labeled. Matter concessions stay matter-local; do not infer a changed standard or create position-drift prompts. Propose a practice-wide change only when the lawyer requests it, through the configured approval path. Persist decision time, target revision, rationale, and resulting revision, even if optional usage telemetry is disabled.

Add a content-update operation and an affected-work query based on evidence links. Verify ownership handling and historical citations using scenario D. Start with explicit refresh and versioned bundled content; continuous external monitoring is deferred.

Evidence links include the sources supporting derived knowledge. Trace them through to work records for impact notices, with cycle handling and an explicit indication when missing links limit coverage.

### 4. Connect one model path and app instructions

Give the app direct instructions for composing the primitives and tools for searching sources, working with matters, recording work, and proposing knowledge changes. Expose domain operations rather than asking the model to construct database statements or filesystem paths.

Replace model-name identity with a stable provider connection ID, endpoint, model, and credential reference on this path. Add a regression test for two endpoints serving the same model, and for an endpoint changed after credentials were stored. Default to fixed official endpoints in initial onboarding.

Evaluate the candidate reference configuration on scenarios A–C. A connection check alone is insufficient: test tool use, grounded answers, follow-up context, structured records, output generation, cancellation, and failure recovery. Provider support follows these results; an allowlist entry is not qualification.

Queries involving restricted matters or sources must respect their policy before sending context to the provider. With only cloud inference configured, a local-only request remains blocked with an explanation. Never remove the restriction to make a demo pass.

### 5. Complete the workspace UI

Wire the earlier interaction design to real records. Make it possible to ask a question across the practice, work in a matter, inspect references and documents, revisit prior work, and decide on proposed learning. Avoid making the user choose a primitive or creating a matter before every question.

Show recorded changes and pending decisions where the work happens. Link citations to source passages and distinguish old from current revisions. Keep model setup a short onboarding/settings task. A general legal workspace, rather than a specialized contract-review screen, must pass A–D.

Chat is the primary interaction. Do not ask the user to choose read/research/evaluate/draft/remember or manually record routine completed work. Support independent simultaneous conversations, visible scope, attached versions, real activity, citation readers, inline approvals, and browsable libraries. Switching chats, opening another browser tab, or closing a tab must not cancel server-owned work. Stop and failure behavior must remain per-response and never save incomplete answers as completed work.

### 6. Package and recover; gate any legacy migration

Complete first-run setup and the OS credential-store integration for the initial packaged target. Choose that target from the tested packaging path before public release; the existing macOS/Linux binaries do not imply equal release qualification.

Add a consistent database-and-artifact backup, restore verification, and interrupted-operation reconciliation. A crash after writing a document but before database registration must leave a recoverable operation, not a misleading completion state. Retry an interrupted work item without duplicating its durable effects; do not imply that a remote model execution can always resume exactly where it stopped.

Before migrating existing standalone users, provide an explicit importer for their Markdown/JSON/JSONL state, a dry-run validation report, a backup, and an inspection step. Unrepresentable legacy fields must be retained or reported. Keep the original source until migration is verified. Plugin data is not converted automatically.

The first milestone qualifies fresh workspaces. Shipping the legacy importer is a later prerequisite for offering existing users migration, not a completion gate for this milestone. Preserve their legacy path in the meantime.

## Milestone completion gates

- All four scenarios work in the application, including a fresh launch and a later reopen.
- Matters, references, knowledge, work, decisions, and citations survive restart with their relationships intact.
- Current retrieval, historical recall, incomplete indexing, and missing evidence behave as specified.
- Automatic recordkeeping, correction, approval, rejection, and source-update handling pass deterministic persistence tests.
- The chosen model configuration passes representative live evaluations on synthetic material; UI tests with fake model output are additional evidence, not a substitute.
- Exported document output is checked using the existing document test machinery and inspected in the supported reader.
- Cancellation, interrupted writes, duplicate retries, source-version conflicts, and backup/restore are exercised.
- Fresh setup reaches useful work without a plugin, source checkout, or manual editing of configuration files.

The first coding slice can finish before this milestone. Report those scopes separately.

## Deferred scope and unresolved choices

Deferred: broad provider discovery, local-model support, task routing, public benchmark UI, advanced practice analytics, bulk reference distillation, scanned-page OCR, connector integrations, background legal monitoring, shared workspaces, and plugin feature parity. Bounded PDF text intake has been brought forward.

Knowledge retrieval, local reference import, automatic matter records, reviewed learning, versioned content updates, and historical recall are in scope. Additional features enter the plan through a demonstrated gap in these scenarios rather than by expanding the provider catalog or adding dashboard panels.

Choices still to resolve: qualified reference model, initial supported OS, and packaged subscription/API onboarding. Validate the installed-CLI integrations against the vendors' documented product conditions and representative live work. Chat-first navigation and independent concurrent conversations are accepted product requirements. These choices do not block deterministic persistence and UI testing.
