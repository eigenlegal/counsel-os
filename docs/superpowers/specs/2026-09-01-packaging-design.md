# Packaging counsel-os as a standalone app — design

**Date:** 2026-09-01 · **Status:** draft for founder review · **Supersedes:** roadmap §9 and the cou-75 notes (wave 1 / wave 2). **Depends on:** the runtime-owned setup spec (content source, `init`, first-run screen) and the Word-documents spec (both shipped in v0.12.0).

## 1. Why

Today counsel-os runs from a git checkout: `bun runtime/src/cli.ts serve …`. A lawyer will not install Bun, clone a repo, or run a build. The founder's philosophy is a standalone app: something to download, drag into Applications, open, sign in, and use. This spec turns the runtime into one binary, then into a Mac app, without changing what the runtime is.

## 2. Scope

**In**
1. A compiled `counsel-os` binary (Bun `--compile`) with the UI, the shipped knowledge content, and everything the runtime reads at start embedded. macOS arm64 and Linux x64 from CI. Self-update.
2. Install paths that need no toolchain: `curl | sh`, a Homebrew tap (formula for the binary, cask for the app), and the plugin hand-off (`/counsel-os:serve` downloads the binary the way browse does).
3. A macOS app: a thin desktop shell around the binary (window, menu-bar item, updater, native folder picker, Keychain), signed with a Developer ID certificate and notarized, shipped as a drag-to-Applications `.dmg`.
4. First-run sign-in for the subscription providers: detect the vendor CLIs, guide the official login, poll until signed in. We never hold vendor credentials.

**Out**
- Windows (the runtime's harnesses do not support it yet). macOS x64 is built only if a runner exists; the last Intel Macs are six years old and Rosetta runs the arm64 binary anyway.
- Bundling the vendors' CLIs inside our binary (479 MB of native binaries). We find and use what the user installed, and we install it for them when asked.
- Browse. It is a plugin skill, not a runtime tool; the app does not ship Playwright or Chromium.
- An app store listing.

## 3. The binary (`counsel-os`)

### 3.1 Build
`bun build --compile --target=bun-darwin-arm64 runtime/src/cli.ts --outfile dist/counsel-os` (and `bun-linux-x64`). A new `bun run build:runtime` script; `release-binaries.yml` adds the two assets `counsel-os-darwin-arm64` and `counsel-os-linux-x64` plus `SHA256SUMS`. The browse assets stay as they are.

### 3.2 What gets embedded
- **UI:** `runtime/ui/dist` via `with { type: 'file' }` imports generated at build time (`scripts/gen_ui_embed.ts` → `runtime/src/server/ui-embed.ts`, git-ignored like the content module). `defaultDistDir()` in `serve.ts` becomes `defaultUi()`: an embedded source when compiled, the dist directory otherwise; `--dist` still overrides.
- **Content:** the existing seam. `contentSourceFor({ compiled: true })` stops throwing and returns the embedded source generated by `generate.ts --embedded`; the build runs it. `knowledge/law/frontmatter-policy.json` joins the embedded set (today it is excluded from content but read by doctor).
- **Detection of compiled mode:** `process.execPath` inside `$bunfs`, exposed as one function `isCompiled()` used by `serve.ts`, `cli.ts`, and the content source.

### 3.3 What stops shelling out
- `docket_sweep` tool → the TypeScript sweep (`runtime/src/vault/docket.ts`) that already powers `/docket`. Delete the Python registration.
- `clean_format` → not registered in the binary. It stays a repo script for the plugin until it is ported (a follow-up; it is a formatting utility, not the hero path).
- Codex's MCP bridge: `codex-harness.ts` spawns `bun …/mcp/stdio.ts`. The binary re-execs itself: `counsel-os mcp-stdio` (a new subcommand that runs the same module), spawned as `process.execPath`. In the checkout the command stays `bun …/mcp/stdio.ts`.

### 3.4 The vendor CLIs
The Claude tier needs the `claude` CLI, the ChatGPT tier the `codex` CLI. We do not bundle either.
- **Locate:** `runtime/src/providers/cli-locate.ts`: PATH, then the vendors' known install locations (`~/.claude/local/claude`, `/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin`, npm's global bin). Result cached per serve.
- **Claude:** pass the located path as `pathToClaudeCodeExecutable` in `claude-harness.ts` (today the SDK resolves its own bundled binary through `node_modules`, which does not exist in a compiled binary). The SDK's `extractFromBunfs` helper is not used, because we do not embed the binary.
- **Codex:** the SDK resolves `codex` through `node_modules` too. First task of the build: confirm whether `@openai/codex-sdk` accepts an executable path; if it does, pass the located one; if not, the harness drives the located `codex` binary directly over the same JSON protocol the SDK uses (the SDK is a thin wrapper; `codex app-server` is the documented surface). This is the one open engineering risk in the spec and gets a spike before the plan.
- **Absent CLI:** the provider row says "not installed · install" and the app can install it for the user (§6).

### 3.5 Home directory and self-update
- `~/.counsel-os` is unchanged (token, runtime.json, providers.yaml, legal-root, backups, content-state in the vault).
- `counsel-os update` (and the app's updater) checks the GitHub release for the running platform, verifies `SHA256SUMS`, replaces the binary atomically, and restarts serve. `counsel-os version` prints the version and the shipped content version. Serve shows "update available" in Settings' Runtime group after a daily check that can be turned off.

## 4. Install paths

- **`curl -fsSL https://eigenlegal.com/install.sh | sh`:** downloads the binary for the platform into `~/.counsel-os/bin/counsel-os`, verifies the checksum, symlinks into `~/.local/bin` (or prints the PATH line), runs `counsel-os init` unless a root exists, prints how to start. The script lives in this repo (`scripts/install.sh`) and eigenlegal.com serves it.
- **Homebrew:** a tap `eigenlegal/homebrew-tap` with `counsel-os` (formula, the binary) and `counsel-os-app` (cask, the `.dmg`). `release.sh` bumps the tap's version and sha automatically after the assets exist.
- **Plugin hand-off:** `/counsel-os:serve` in the plugin downloads the binary like `find-browse` does today (same locator shape, `COUNSEL_OS_NO_DOWNLOAD=1` respected) and runs it, so plugin users get the app without a checkout.

## 5. The macOS app

### 5.1 Shape
A thin **Tauri v2** shell (Rust, WKWebView). Not Electron. The shell:
- ships the `counsel-os` binary as a sidecar and starts it on launch (`serve` on a free port, `--no-open`),
- opens one window at the app's URL; the first visit carries the token read from `runtime.json`, after which the session cookie keeps the browser signed in, so the shell never touches auth again,
- adds a menu-bar item (open, restart runtime, check for updates, quit) and a Dock icon,
- exposes a native folder picker and the Keychain to the web UI through a tiny bridge (`window.counselShell`): the first-run screen uses the picker for "Or another folder"; the providers track will use the Keychain for API keys. The web UI works without the bridge (the browser build stays the same).
- updates itself with Tauri's updater (signed manifest on the GitHub release), which also replaces the sidecar.

### 5.2 Signing and notarization
- A **Developer ID Application** certificate under the Eigen Software LLC Apple team (P48959FPAN). This does not exist today; the founder creates it once in the developer portal and exports it to the CI keychain (a GitHub secret), the way the App Store Connect key is kept for the iOS apps.
- CI: `codesign` with hardened runtime and the sidecar's entitlements, `xcrun notarytool submit` with the existing ASC API key (`--key/--key-id/--issuer`), staple, then `create-dmg` with the drag-to-Applications layout. Assets: `Counsel OS-<version>-arm64.dmg`, `latest.json` for the updater.
- Local `bun run app:build` produces an unsigned app for development.

### 5.3 What the app must never do
Store vendor credentials, phone home, or bypass the runtime's auth (the shell reads the token from a 0600 file the runtime wrote; it does not generate one).

## 6. First-run sign-in
The first-run screen (v0.12.0) lists providers with states from `GET /setup/providers`. This spec adds the actions:
- **"install"** for a missing CLI: the runtime knows the official install command per vendor; in the app, a button runs it in a bounded subprocess with its output streamed to the screen in set text; in the browser, the command is shown to copy.
- **"sign in"** for an installed, signed-out CLI: the app opens the vendor's login (`claude login` / `codex login`) in Terminal.app (the flows are interactive and open the browser) and polls `GET /setup/providers` until the state flips; the row updates in place. We orchestrate the vendor's own login, nothing else.
- Ollama: "install" links the official installer; "start" runs `ollama serve` if installed and stopped; the model list comes from the API.

## 7. Error handling
- No CLI found after install: the row shows the paths we searched and a "locate" field.
- Sidecar fails to start: the window shows the runtime's last log lines in set text and a "restart" action; nothing else in the shell has state to lose.
- Update download fails or checksum mismatch: the current binary is untouched; one sentence in Settings.
- Notarization missing (a dev build): macOS's own dialog; documented in CONTRIBUTING.

## 8. Testing
- Unit: `isCompiled`, the embedded UI/content sources (list and read parity with the repo source), `cli-locate` on a temp PATH, the `mcp-stdio` re-exec, the update checker against a fixture release JSON.
- CI smoke on the built binary: `counsel-os version`, `serve` on a temp home with no vault → `/health` reports setup mode, `init --yes` on a temp vault → `serve` → `/vault/overview` lists the sample matter, `docx read` on the sample NDA. Run on both platforms' artifacts.
- Manual before the first `.dmg` release (virgin-hardware gate, per CONTEXT): a clean Mac, download the `.dmg`, drag, open, sign in with Claude, review the sample NDA, redline it.

## 9. Staging and order
1. **Binary:** embed UI + content, `isCompiled`, docket tool on TS, `mcp-stdio` re-exec, `cli-locate` + Claude path; the Codex spike; `build:runtime`; CI assets + smoke. Ships as a release asset next to the browse ones.
2. **Install paths:** `scripts/install.sh`, the tap, `release.sh` bumps, the plugin's `/counsel-os:serve` hand-off, self-update.
3. **App:** Tauri shell with sidecar, window, menu bar, folder picker bridge; unsigned dev build; docs.
4. **Signing:** certificate (founder), CI signing + notarization + `.dmg` + updater manifest.
5. **Sign-in actions** on the first-run screen and Settings.

Each step is its own PR with QA; step 4 needs the founder for the certificate.

## 10. Open questions for the founder
