# Runtime-owned setup and content — design

**Date:** 2026-09-01 · **Status:** draft for founder review · **Decision it implements:** founder ruling 2026-09-01: the runtime carries the knowledge content and owns first-run setup. The Claude Code plugin stays as a front end.

## 1. Why

A lawyer who installs the standalone app and never ran the Claude Code plugin cannot start: `serve` exits with "No Counsel OS legal root found. Run /counsel-os:setup". The setup lives in `skills/setup/SKILL.md` and seeds 3.8 MB of content (26 law areas, 24 standards, 35 methods, 21 library categories, memory patterns) from the plugin checkout. `update`, `law-refresh`, and `doctor` maintain it, all as skills the model runs. For the app to stand alone the runtime must carry the content, create the vault, and keep the content current, in TypeScript, with a first-run screen instead of an interview.

## 2. Scope

**In:**
- A content source abstraction: the same files, loaded from the repo in development and embedded in the compiled binary.
- `counsel-os init` (CLI) and a setup API the UI drives. Serve starts in setup mode when no root exists instead of exiting.
- First-run screen in the web UI: vault location, identity (three answers), one practice question, provider check, optional sample matter, seed.
- Managed content updates in the runtime: detect changed law areas and practice seeds by content hash; apply per the same ownership rules as the `update` skill.
- A read-only `doctor` in the runtime (`GET /doctor`) covering the vault checks; the environment checks that only mattered for Python and pandoc are dropped.

**Out:**
- Removing the plugin's setup/update/doctor skills. They stay; they write the same files, so either front end can bootstrap or maintain a vault. Later they can call the runtime.
- QMD. The runtime's own search covers the app; the plugin keeps its optional qmd offer.
- The compiled binary and installer packaging themselves (roadmap §9, cou-75). This spec makes the content embeddable; packaging is the next spec.
- Sign in with Claude / ChatGPT buttons. The first-run provider step detects what is available and picks a default; the sign-in flows come with the installer work.

## 3. Content source

```
runtime/src/content/
  manifest.ts    the list of shipped groups + files + content hashes (generated)
  source.ts      ContentSource: { list(group), read(path), version }
  repo.ts        reads from the checkout (pluginRoot/knowledge, /templates, /primitives, /skills/counsel)
  embedded.ts    reads from files embedded at compile time
```

- **Groups:** `law/<area>` (26), `practice-seed/standards`, `practice-seed/methods`, `practice-seed/library`, `practice-seed/reference`, `practice-seed/profile`, `templates/memory`, `primitives`, `counsel-skill`. The manifest is generated by `scripts/gen_content_manifest.ts` at release time from `.content-versions.json` plus per-file SHA-256 of the frontmatter-stripped body (the same hashing `bump_content_versions.py` uses, ported).
- **Embedding:** Bun's `--compile` embeds files imported with `with { type: 'file' }`. `embedded.ts` is generated alongside the manifest so the import list is explicit. In development `pluginRoot` resolution stays as it is and `repo.ts` is used; the choice is made once in `serve.ts` by whether `import.meta` reports a compiled binary.
- **Primitives and the counsel skill** move behind the same source, so `prompt.ts` and `primitives.ts` stop reading `pluginRoot` directly.

## 4. Setup mode

`serve` no longer exits when no root resolves. It starts with `state.vault = null`, serves the UI, and every vault-backed route answers `409 { error: 'setup-required' }`. `/health` reports `setup: true`. The UI shows the first-run screen whenever health says so.

**CLI:** `counsel-os init [--vault <dir>] [--name … --org … --role in-house|outside|solo --jurisdiction … --practice "…"] [--sample-matter] [--yes]`. Non-interactive with flags; otherwise the same questions as the UI on stdin. Both paths call the same `runSetup(plan)` in `runtime/src/setup/`.

**API:**
- `GET /setup/detect` → candidate vault locations: the conventional roots the resolver already scans, Obsidian vaults found the way the setup skill finds them (read-only), and the default new location `~/Documents/Counsel OS`. Each with `{ path, kind: 'existing-root' | 'obsidian-vault' | 'new', writable }`.
- `GET /setup/providers` → which providers are usable right now: `claude-sub` (claude CLI present and logged in), `codex-sub`, `ollama` (server reachable, models listed), plus whether an API key env var is set. The runtime already knows how to probe each harness; this reuses the provider test path without spending a model call where a cheaper check exists.
- `POST /setup` with the plan `{ vault, identity: { name, organization, role, jurisdiction }, practice: string, sampleMatter: boolean, defaultProvider }` → runs setup, then switches the live server onto the new vault without a restart (`state.vault` is set, the token is unchanged, the UI reloads health and goes Home).

**`runSetup` writes exactly what the skill writes:** `config.md` (marker + commented overrides), `~/.counsel-os/legal-root` pointer, `law/` (196 files), `practice/{profile,standards,methods,library,reference}`, `memory/patterns.md`, empty `matters/` and `entities/`, `.gitignore`, and `git init` + initial commit when git is available. The profile is the Express template with the same branch: the in-house software answer gets the tuned profile, everything else the general one. Idempotent: an existing marked root is adopted, not re-seeded; missing groups are added, existing files never overwritten.

**Sample matter (opt-in):** `matters/sample-mutual-nda/` with the synthetic NDA (`skills/demo/assets/sample-mutual-nda.docx` and `.md`) and a `matter.md` (`counsel-os-type: matter`, `sample: true`, stage `intake`, next action "Ask counsel to review the NDA against our confidentiality standard"). Home shows it like any matter; the reader shows the `.docx` once the docx spec's stage 1 lands. It can be deleted from the vault like anything else.

## 5. First-run screen (UI)

One page, four steps, no wizard chrome. Serif heading "Set up counsel-os." with the double-rule ledger groups:

1. **Where your documents live.** A list of detected locations as rows (path, kind in small caps: "Obsidian vault", "Counsel OS root", "New folder"), the default new location preselected when nothing exists. A "Choose another folder" field (typed path; the desktop shell later replaces it with a native picker).
2. **Who you are.** Name, organization, role (in-house / outside / solo as set-text choices), jurisdiction. Four fields.
3. **What you practice.** One free-text line, the Express question verbatim. Under it, one sentence explaining what it tunes.
4. **Which model answers.** The rows `GET /setup/providers` returns, each with its state in set text ("signed in", "not installed", "running · 3 models"), the first usable one preselected. A line under it: "You can change this any time in Settings."

Then a checkbox row "Add a sample matter (a synthetic NDA) so you can try a review right away" (on by default), and one button "Create". Progress in set text ("Writing 26 law areas…"), then Home. Every failure reads as a sentence next to the step it belongs to; the page never resets what was typed.

Mockups: `docs/superpowers/specs/img-standalone/mock-setup.html` (the form) and `mock-setup-progress.html` (progress, then a failed step with the typed values intact), rendered as `setup.png` / `setup-progress.png` (and `-dark`) beside them. The screen has no rail: there is no vault for the rail to point at yet. Detected locations read as ledger rows (path in mono, kind in small caps, the chosen one marked by the set-text word "selected", the others by "use this"). Providers read the same way, with the state in set text ("signed in", "not installed", "running · 3 models").

## 6. Content updates in the runtime

`runtime/src/content/update.ts` ports the `update` skill's rules:
- Law is plugin-managed by default. For each shipped law file, compare the vault file's body hash to the shipped hash and to the hash the vault last received (recorded in `.counsel/content-state.json` at seed and update time). Unchanged-by-user and changed-upstream → apply. Changed-by-user (`managed-by: user`, or `law_management: user` in `config.md`, or the vault hash differs from the last received) → report, never overwrite. Vault-only areas are never touched.
- Practice is user-owned. Never seed-vs-vault diffed. An upstream change is detected against the last received seed hash and reported as a diff for the user to merge; the `## Our Position` sections are preserved by the merge helper the skill already describes.
- Surfaces: `counsel-os update-content` (CLI), `GET /content/status` (what is pending), `POST /content/apply` with the approved list. Settings gets a "Content" group: version shipped, version in the vault, "N law areas have updates · review". Never automatic unless `auto_apply_law_updates: true` in `config.md`, which the runtime honours.

## 7. Doctor in the runtime

`GET /doctor` returns the vault checks ported from the skill: root and marker consistency, structure and counts, law currency (`last-reviewed` + cadence), standards ↔ library ↔ law-floor consistency, matter-aware law impact, git state, backups. Environment checks that exist only for Python, pandoc, or the browse binary are dropped. Settings' Runtime panel gains a "Check the vault" action that shows the findings in set text. The plugin's `/counsel-os:doctor` keeps its own copy until it is switched to call the endpoint.

## 8. Error handling

- Vault path not writable, or inside the plugin tree: refuse with the reason, before writing anything.
- Partial seed failure (disk full, permission): the setup stops, reports the group that failed and what was written; a rerun completes the missing groups (idempotent).
- No usable provider: setup still completes; Home shows the provider-not-available notice with the Settings link.
- Git absent: skip the repo step and say so in the completion line.

## 9. Testing

- `content`: manifest generation is deterministic; the embedded and repo sources list identical groups and hashes (a test runs both against the checkout).
- `setup`: a temp home + temp vault; seeds, marker, pointer, counts, idempotence on rerun, adoption of an existing marked root, profile branching, sample matter.
- Routes: setup mode 409s, `/setup/detect` on a temp tree with a planted Obsidian vault, `/setup` end to end and the live switch, `/content/status` and `/content/apply` with a user-modified law file that must be reported not overwritten.
- UI: first-run screen states, a failed step keeping the typed values, the Content group in Settings.
- The existing `resolve-root` tests keep passing unchanged.

## 10. Staging and order

1. Content source (repo + generated manifest), primitives and counsel skill loaded through it. No behaviour change.
2. `runSetup` + `counsel-os init` + tests. Serve's setup mode and the 409s.
3. First-run screen (after mockup review) + `/setup/*` routes + live switch.
4. Sample matter.
5. Content updates + Settings "Content" group.
6. Doctor endpoint + Settings action.
7. Embedded source generation wired into the binary build (lands with the packaging spec).

Each step is its own PR with QA.
